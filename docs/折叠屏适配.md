# 折叠屏适配执行文档

一次只做一步。该步的验收通过后，再开始下一步。不要在同一步里夹带后面的内容。

本文件只负责窗口布局。`docs/执行文档.md` 里的学习路径、进度、积分和文案，这一轮不要改。

本轮的完成标准：手机竖屏、iPhone Duo 外屏、Duo 内屏、半折、平板整窗和平板分屏，用同一套判断。窄窗口仍是现在的底栏和整页进入。宽窗口把底栏换成侧栏；只有放得下的列表-详情才左右分栏。半折时正文、按钮和练习命中区不压在折痕上。

这一轮不接平行视界，不接 Activity Embedding。

## 判断

数字锁在这里。后面的步骤用这组数，不要另设一套断点，也不要按机型名、`UIDevice.userInterfaceIdiom` 或「是不是平板」分支。

| 名字 | 值 | 用途 |
|---|---|---|
| 高窗口的最小高度 | 480 | 外屏横屏 466 高，停在窄窗口 |
| 未拿到 size class 时的最小可用宽度 | 600 | 只在 iOS 通道还没返回时使用 |
| 侧栏预留 | 80 | `NavigationRail` 图标在上、文字在下，不要用 `extended: true` |
| 列表栏宽 | 240 | 双栏左侧就用这个宽度，不要改成 320 |
| 详情最小宽 | 320 | 扣掉侧栏和列表后不够，就不要双栏 |
| 阅读最大宽 | 720 | 学习首页、章节、测验、资料正文、练习列表、个人页 |
| 表单最大宽 | 440 | 注册、助记词、恢复、三句话、昵称 |

可用宽度 = 窗口宽度 − 左安全区 − 右安全区。左右分开减。不要用两边里较大的那个再乘 2。高度用窗口高度，不减上下安全区。

`HorizontalSizeClass` 只有 `compact`、`regular`、`unspecified`。

- `compact`：窄窗口。外屏横屏宽 678 也算窄。
- `regular` 且高度 ≥ 480：宽窗口。
- `unspecified` 且高度 ≥ 480 且可用宽度 ≥ 600：宽窗口。Android 一直走这条。iOS 通道还没返回时也走这条。
- 宽窗口，并且可用宽度 − 80 − 240 ≥ 320：可以双栏。Duo 内屏竖屏 669、安全区为 0 时，余量是 29，可以双栏。不要把列表加宽到把这 29 吃掉。
- `regular` 但扣掉安全区后不够 640：宽窗口，只出侧栏，内容仍是单栏。平板分到大约 507 宽时就是这种。

安全区很大时允许退回单栏。不要为了凑满 669 忽略安全区。

iOS 的水平 size class 用 `MethodChannel`，名字 `digi_players/size_class`，方法 `getHorizontalSizeClass`，返回 `compact`、`regular` 或 `unspecified`。只在启动后第一帧和 `didChangeMetrics` 时要一次。不要在 `build` 里调用。Android 没有这个通道时保持 `unspecified`，不要当成错误。拿到新值之前可以用宽高兜底，但不要把兜底结果记成「这台设备是手机」。开合和分屏都会在会话中途改窗口。

Flutter 的 `MediaQuery.displayFeatures` 目前只在 Android 有折痕。iOS 折痕放到步骤 7，不要提前做。

## 本轮不做

执行各步时不要顺手做这些：

- 平行视界、各厂商 EasyGo、`easygo.json`
- Activity Embedding、第二个 `FlutterEngine`、第二套 `FlutterActivity`
- `foldable`、`duo_fold`、`flutter_adaptive_scaffold`，或其他自适应包
- 把折痕写进全局 `MediaQuery.displayFeatures`。那样对话框和底部表单会被切到半边
- 学习首页、章节、测验、四个练习做成左右两栏
- 练习进行时藏起侧栏
- 按机型字符串分支，或锁定横竖屏
- 改路由路径、学习路径、积分、广场房间和 WebSocket
- 改 `docs/执行文档.md` 和 README

## 步骤 7 · 折痕

状态：已完成。折痕计算在 `lib/core/layout/window_layout.dart`，不写回 `MediaQuery`。竖缝会挪动双栏分界；章节、测验、资料详情和助记词通过 `ReadingWidth` 整段让到较宽一侧。P2P 画布按让开折痕后的矩形计算。拼图、哈希、反诈整页让到较大一侧。iOS 没有折痕接口时返回不活跃。

现状：Android 引擎会把铰链和折痕放进 `MediaQuery.displayFeaturesOf`。`DisplayFeatureType.fold` 与 `hinge` 都算折痕，`cutout` 是刘海，步骤 2 的安全区已经负责，这里不要再处理。iOS 上这份列表是空的。完全展开时折痕宽度为 0，或 iOS 的 division 标记为不活跃。半折时才有一条要让开的区域。

改这些文件：

- `lib/core/layout/window_layout.dart` 可以增加折痕矩形的纯计算，方便测试。不要把结果写回 `MediaQuery`。
- `lib/features/games/p2p_game/p2p_game_screen.dart`
- 章节、测验、资料详情、助记词这几页，如果一行会穿过折痕，就把整段放到较宽的一侧。
- `ios/Runner/AppDelegate.swift`：在同一个 `FlutterViewController` 上再注册一个方法 `getFoldDivision`。返回 `{active, left, top, width, height}`，单位是逻辑像素，坐标系跟当前视图一致。`active` 为 false 时宽高返回 0。Android 不实现这个方法。

什么时候算「有一条要让开的缝」：

- Android：类型是 `fold` 或 `hinge`，并且姿态是 `postureHalfOpened`，或者这条区域的短边 ≥ 8。姿态是 `postureFlat` 且短边 < 8：没有缝。
- iOS：只有 `active == true` 才有缝。通道缺失就当作没有缝，步骤 1 到 6 的布局继续用。
- 短边是水平方向的，当作竖折痕。短边是垂直方向的，当作横折痕。

竖折痕：

- 当前页面正在双栏：分界移到折痕，中间空出折痕的宽度。折痕左边去掉侧栏后若小于 200，或右边小于 280，这一页退回侧栏加单栏，整页放在较大的一侧。
- 阅读页和表单：内容放在与折痕不相交的较宽一侧。行宽限制仍有效。
- P2P：`LayoutBuilder` 的命中和 `CustomPaint` 都使用让出折痕之后的矩形。节点坐标按这个矩形的宽高计算，不要先按整块父级算出位置再平移。

横折痕：

- P2P：折痕以上是关卡说明和画布，以下是图例和操作。某一侧高度小于 160 时不切，整页放在较高的一侧。
- 拼图、哈希、反诈：主按钮不要落在折痕矩形里。做不到自然的上下分时，整页放在较高的一侧。不要为了这三页重做关卡布局。
- 学习首页、资料、聊天、设置不改成上下两栏。

验收：

- 纯计算测试：平坦且短边 0，双栏分界仍是原来的 240。半折竖缝位于 x = 360、宽 16，分界移到这条缝。缝把一侧挤到最小宽度以下时，结果是单栏。
- P2P 在一条竖缝穿过画布时，节点中心都不落在缝的矩形里。点击缝上的位置不会选中节点。
- 助记词页在竖缝穿过中间时，词卡整体在缝的一侧，不跨缝。
- 完全展开、缝宽为 0：资料双栏和步骤 4 的验收一样，中间没有一条 16 宽的空带。
- iOS 通道失败：应用仍按步骤 1 到 6 显示，不白屏。

## 本轮验收

测试先过。没有折叠屏或平板时，测试通过就是这一轮过了。不要为了手测去加厂商分屏配置。

有设备时再看这几眼：

1. 手机竖屏：底栏仍是学习、练习、我的。资料点进去是整页，返回回到目录。
2. Duo 外屏横屏：仍是底栏和整页。不要因为比较宽就出侧栏。
3. Duo 内屏竖屏、完全展开：学习 / 练习 / 我的仍带侧栏。资料、广场、设置进入后藏侧栏，只剩列表|详情两栏。学习首页仍是继续卡在中间，不是两列。四个练习铺满侧栏右侧。
4. 把内屏慢慢合上再打开：不用杀进程。合上是外屏布局，打开回到刚才的路由，双栏或单栏跟着窗口变。
5. 半折成书：资料的分界让开折痕。助记词不跨在折痕上。P2P 的节点能点到。
6. 平板整窗与分到大约一半：整窗和内屏同一类；一半宽时有侧栏，内容是单栏。
7. 学习路径、积分、广场房间和设置里的助记词说明与这一轮之前一致。



总结一个折叠屏适配方案，方便其他同事接入。可以复用，不重复编写。

目前看到两种情况，1.底部导航栏在左侧，2底部导航栏在底部（变成文字标题按钮）
1. 按窗口尺寸做自适应，不按设备类型。

前端开发要注意的坑
不要锁方向。 Flutter 文档提醒，锁方向在折叠屏上会导致展开后出现黑边（letterbox）。而且 面向 Android 17 的 App，在 600dp 以上的大屏上，方向、可缩放性、宽高比限制都会被系统忽略，锁了也没用。 
flutter
折叠/展开时不能丢状态。 官方的说法是 Flutter 默认会保留状态，如果丢了，要检查所用插件是否支持大屏设备。重点排查原生插件、WebView、相机、支付/风控 SDK，以及表单、滚动位置和路由栈。如果你做金融类流程，"填到一半折叠就丢数据"是最容易被用户投诉的场景。 
flutter
断点切换时别换 key 或重建子树。 社区总结过一个典型问题：不同断点用不同 slot/key，会导致 折叠屏展开时整个 body 子树重建，滚动位置和表单输入全部丢失。 
dev
不要硬编码设备尺寸，也不要用 MediaQuery.size 当"设备大小"。 多窗口下它只是窗口大小，官方为此加了基于 Display 的 API。
别把关键控件放在折痕上。
测试矩阵要补上。 至少要覆盖 Android 折叠屏模拟器的几种姿态、分屏和小窗，以及不同字体缩放。
